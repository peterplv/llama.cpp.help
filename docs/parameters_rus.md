**-t,    --threads N**<br>
number of CPU threads to use during generation<br>
(default: -1)<br>
(env: LLAMA_ARG_THREADS)

Комментарий:<br>
Число CPU-потоков для генерации. В теории, чем больше потоков, тем выше скорость работы.

Ремарка:<br>
Генерация упирается в пропускную способность памяти, поэтому после некоторого числа потоков прирост почти исчезает, а лишние потоки даже могут замедлить скорость генерации, это нужно проверять на конкретной конфигурации и модели.<br>
Также есть мнение, что для процессоров серии Ryzen лучше указывать число физических ядер, тогда как для Intel число логических ядер.

По умолчанию: "--threads -1" (автовыбор).

env: LLAMA_ARG_THREADS - переменная окружения в ОС, в ней можно указать значение этого параметра для текущей сессии.
<br>
<br>

**-tb,   --threads-batch N**<br>
number of threads to use during batch and prompt processing<br>
(default: same as --threads)

Комментарий:<br>
Число CPU-потоков для обработки входящего промпта и батчей токенов (prefill). Если не задан, берется значение "--threads".<br>
В целом всё как в "--threads", только там речь о генерации токенов и работе llama.cpp в целом, а здесь о только о prefill.

Ремарка:
Генерация упирается в пропускную способность памяти, поэтому после некоторого числа потоков прирост почти исчезает. Обработка промпта хорошо масштабируется по потокам, поэтому в теории для "--threads-batch" оптимально большее число потоков, чем для общего "--threads", но это нужно проверять на конкретной конфигурации и модели.

По умолчанию: "--threads-batch -1" (автовыбор).
<br>
<br>

**-C,    --cpu-mask M**<br>
CPU affinity mask: arbitrarily long hex. Complements cpu-range<br>
(default: "")

Комментарий:<br>
Указать использование конкретных CPU-ядер через битовую маску в шестнадцатеричном формате.<br>
Пример: "--cpu-mask 0xF" (0xF = 1111, использовать ядра CPU0, CPU1, CPU2, CPU3).

По умолчанию: не используется (маска не задана).
<br>
<br>

**-Cr,   --cpu-range lo-hi**<br>
range of CPUs for affinity. Complements --cpu-mask

Комментарий:<br>
Указать использование конкретных CPU-ядер в заданном диапазоне. Дополнительный способ указать привязку к конкретным CPU-ядрам в заданном диапазоне. В отличии от "--cpu-mask" задается в привычном десятичном виде. Можно использовать оба параметра одновременно "--cpu-mask" + "--cpu-range".<br>
Пример: "--cpu-range 0-7" (ядра от 0 до 7, всего 8).

По умолчанию: не используется (не задано).
<br>
<br>

**--cpu-strict <0|1>**<br>
use strict CPU placement<br>
(default: 0)

Комментарий:<br>
Дословно "использовать строгое размещение на CPU". Работает вместе с "--threads/--cpu-mask/--cpu-range".<br>
Без strict потоки "--threads" могут свободно перемещаться между ядрами CPU по усмотрению ОС. Со strict каждый поток жёстко закрепляется за отдельным ядром.

Возможные плюсы: меньшие задержки, более оптимальная работа кэша. Главный выигрыш от привязки в том, что потоки не переносятся между CPU и не теряют кэш. Но это только в теории, в большинстве случаев разница в задержках крайне незначительная. Причем, иногда strict может навредить, например если другой процесс занял один из закреплённых CPU, текущий поток не может уйти на свободный CPU и ждёт.

По умолчанию: "--cpu-strict 0" (отключено).
<br>
<br>

**--prio N**<br>
set process/thread priority: low(-1), normal(0), medium(1), high(2), realtime(3)<br>
(default: 0)

Комментарий:<br>
Приоритет процесса llama.cpp в планировщике процессов ОС. Чем выше приоритет, тем llama.cpp получает больше CPU-времени при конкуренции с другими процессами в системе. Влияет только при конкуренции за CPU: на свободной системе разницы практически нет.

Возможные значения:<br>
- (-1) low - фоновый режим, llama.cpp уступает другим процессам.<br>
- 0 (normal, по умолчанию) - llama.cpp конкурирует с другими процессами на равных. Для большинства случаев лучший выбор.<br>
- 1 (medium) - llama.cpp получает немного больше CPU, чем другие процессы.<br>
- 2 (high) - llama.cpp получает существенно больше CPU, остальные процессы меньше.<br>
- 3 (realtime) - llama.cpp получает максимальный приоритет. Могут начать тормозить системные процессы, использовать не рекомендуется.

Для приоритетов medium(1), high(2), realtime(3) может понадобиться администраторский доступ, иначе llama.cpp просто проигнорирует эту директиву.

По умолчанию: "--prio 0" (normal).
<br>
<br>

**--poll <0...100>**<br>
use polling level to wait for work
(0 - no polling, default: 50)

Комментарий:<br>
Определяет, как долго поток активно ожидает новую работу после завершения текущей операции (polling).

На примерах:<br>
"--poll 0" - поток засыпает сразу. Минимальная нагрузка на CPU, но пробуждение чуть дольше.<br>
"--poll 100" - самое длительное активное ожидание. Пробуждение почти моментальное, но выше нагрузка и энергопотребление CPU.<br>
Разница обычно очень не значительная, миллисекунды на токен, может быть немного заметна только на маленьких и быстрых моделях.

По умолчанию: "--poll 50".
<br>
<br>

**--prio-batch N**<br>
set process/thread priority: 0-normal, 1-medium, 2-high, 3-realtime<br>
(default: 0)

Комментарий:<br>
Тоже самое, что "--prio", только для потоков обработки промпта и батчей (prefill). Чем выше приоритет, тем потоки батчей в llama.cpp получают больше CPU при конкуренции с другими процессами в системе. Влияет только при конкуренции за CPU: на свободной системе разницы практически нет.<br>

В режиме realtime(3) prefill llama.cpp будет вытеснять все остальные процессы в системе, в том числе системные, ОС начнет сильно тормозить.

Возможные значения:<br>
- 0 (normal, по умолчанию) - llama.cpp prefill конкурирует с другими процессами на равных. Для большинства случаев лучший выбор.<br>
- 1 (medium) - llama.cpp prefill получает немного больше CPU, чем другие процессы.<br>
- 2 (high) - llama.cpp prefill получает существенно больше CPU, остальные процессы меньше.<br>
- 3 (realtime) - llama.cpp prefill получает максимальный приоритет. Могут начать тормозить системные процессы, использовать не рекомендуется.

Для приоритетов medium(1), high(2), realtime(3) может понадобиться администраторский доступ, иначе llama.cpp просто проигнорирует эту директиву.

По умолчанию: "--prio-batch 0" (normal).

**-c,    --ctx-size N**<br>
size of the prompt context<br>
(default: 0 - loaded from model)<br>
(env: LLAMA_ARG_CTX_SIZE)

Комментарий:<br>
Длина контекста. Обычно указывается длина контекста модели (если позволяет вместить память). Чем больше длина контекста, тем больше требуется памяти для работы с ним. Часто имеет смысл указать меньший размер контекста, например для коротких чатов или единичных запросов, например таких как вызовы функций/инструментов.

По умолчанию: "--ctx-size 0" (используется значение модели).

env: LLAMA_ARG_CTX_SIZE - переменная окружения в ОС, в ней можно указать значение этого параметра для текущей сессии.

**-n,    --predict, --n-predict N**<br>
number of tokens to predict<br>
(default: -1, -1 = infinity)<br>
(env: LLAMA_ARG_N_PREDICT)

Комментарий:<br>
Сколько токенов модель будет генерировать. При достижении указанного значения генерация текста прекратится (резко оборвется). Если не указать этот параметр, либо указать "--predict -1" (по умолчанию), то текст будет генерироваться до бесконечности или до завершающего токена (если таковой имеется для используемой модели).<br>
Считаются только новые токены, токены промпта сюда не входят.

Примечание:<br>
Завершающий токен (EOS/EOG) это специальный токен, которым при обучении заканчиваются тексты, так модель учится понимать, когда нужно закончить генерацию текста. Завершающие токены могут отличаться в разных моделях. Примеры завершающих токенов: <|endoftext|>, <end_of_turn>, </s>, <|im_end|> и тд.

По умолчанию: "--n-predict -1" (бесконечно или до завершающего токена).

Важно:<br>
Для llama-completion есть еще один вариант значения для этого параметра:<br>
"-2 = until context filled", дословно это переводится как "пока контекст не будет заполнен". То есть, генерация прервется при достижении заданной длины контекста (смотрите "--ctx-size").<br>

Я пока затрудняюсь сказать, почему этот вариант есть только для llama-completion. Возможно дело в особенностях работы разных утилит: llama-cli и llama-server обычно работают в режиме диалога (бэкенд заточен под это), тогда как llama-completion работает исключительно в режиме генерации одного сообщения (разовый вызов).

env: LLAMA_ARG_N_PREDICT - переменная окружения в ОС, в ней можно указать значение этого параметра для текущей сессии.

**-b,    --batch-size N**<br>
logical maximum batch size<br>
(default: 2048)<br>
(env: LLAMA_ARG_BATCH)

Комментарий:<br>
Размер батча в токенах. Используется для входящего запроса (prefill - промпта, сообщения или цепочки сообщений). Если prefill большой, тогда он будет разбит на батчи, которые отправятся в последовательную обработку. Деление на батчи нужно для экономии памяти при вычислениях.

По умолчанию: "--batch-size 2048".

env: LLAMA_ARG_BATCH - переменная окружения в ОС, в ней можно указать значение этого параметра для текущей сессии.
<br>
<br>

**-ub,   --ubatch-size N**<br>
physical maximum batch size<br>
(default: 512)<br>
(env: LLAMA_ARG_UBATCH)

Комментарий:<br>
Суть параметра как "--batch-size", только здесь указывается "физический" размер батча (микробатч), который фактически отправится в CPU/GPU.<br>
Например, если "--batch-size 2048", а "--ubatch-size 512", тогда "софтовый" батч в 2048 токенов будет разбит на физические батчи по 512 токенов, которые отправятся на вычисления в CPU/GPU.

Важно: значение "--ubatch-size" должно быть не больше "--batch-size", иначе в этом параметре нет смысла, т.к. исходный размер батча задается в "--batch-size", а "--ubatch-size" помогает лишь тем, что разбивает батч перед отправкой на CPU/GPU и не может быть больше исходного размера батча.

По умолчанию: "--ubatch-size 512".

env: LLAMA_ARG_UBATCH - переменная окружения в ОС, в ней можно указать значение этого параметра для текущей сессии.
<br>
<br>

**--keep N**<br>
number of tokens to keep from the initial prompt<br>
(default: 0, -1 = all)

Комментарий:<br>
Сколько токенов из начального промпта оставить в случае переполнения контекста, от остальной части убрать первую половину (старые токены).<br>
Когда контекст ("--ctx-size") заканчивается, llama.cpp начинает обрезать токены с начала беседы, это называется context shift. Благодаря параметру "--keep" можно сохранить начало диалога, например полностью сохранить системный промпт, а окно контекста начнет обрезаться только после указанного значения.

Пример:<br>
\[n_past, n_left, n_discard - внутренние переменные llama.cpp, они вычисляются в процессе работы\]

--ctx-size 4096, --keep 200, контекст заполнился (n_past = 4096).<br>
n_left = 4096 - 200 = 3896 (не трогаем первые 200 токенов).<br>
n_discard = 3896 / 2 = 1948 (из оставшихся 3896 удаляем половину - более ранние 1948 токенов).<br>
При последующем заполнении контекста (n_past), context shift повторяется.<br>

Если "--keep -1", тогда сохраняется весь входящий промпт.

По умолчанию: "--keep 0" (без сохранения).
<br>
<br>

**--swa-full**<br>
use full-size SWA cache<br>
(default: false)

Комментарий:<br>
Некоторые модели, например Gemma2/3, используют Sliding Window Attention (скользящее окно внимания) вместо полноценного внимания по всему контексту. По умолчанию llama.cpp оптимизирует SWA-кэш и хранит только нужное (ограниченное) окно внимания, это существенно экономит память. Если указать "--swa-full", тогда включится полноразмерный SWA-cache без оптимизации. Полный SWA cache теоретически может дать лучшее качество и лучшую совместимость/стабильность, но требует существенно большего объема памяти для хранения всего KV-кэша.

По умолчанию: не используется.
<br>
<br>

**-dt,   --defrag-thold N**<br>

(env: LLAMA_ARG_DEFRAG_THOLD)

Порог "-dt" задавал долю дыр в памяти, после которой запускалась дефрагментация. В новых версиях llama.cpp кэш умеет размещать токены в не связанных ячейках, поэтому дефрагментация больше не нужна. Параметр сохранён для совместимости.

\[Ремарка: описание работы параметра может быть не точным\]

Выбор способа загрузки файла модели в память. Заменяет старые параметры "--mmap", "--no-mmap", "--mlock" и "--direct-io".

Возможные варианты:<br>
- auto (по умолчанию) - использует mmap, если устройство это поддерживает.<br>
- none - особый режим не используется: llama.cpp полностью считывает файл модели с диска в выделенную оперативную память. Загрузка дольше, зато модель находится целиком в памяти и повторные обращения к диску не происходят. Фактически аналог старого "--no-mmap".<br>
- mmap - файл модели отображается в адресное пространство процесса llama.cpp, а ОС подгружает нужные страницы в RAM (page cache) по мере обращения. Дает более быстрый старт, повторные запуски почти мгновенные, но при нехватке RAM ОС может выкинуть часть страниц и потом перечитать их с диска заново. Аналог старого "--mmap".<br>
- mlock - запретить ОС выгружать модель из RAM в SWAP (файл подкачки) и сжимать её. Меньше возможных фризов, стабильнее скорость работы, но требует достаточного объема памяти. Аналог старого "--no-mmap --mlock" (модель читается в RAM и закрепляется там).<br>
- mmap+mlock - модель отображается через mmap, и все её страницы закрепляются в RAM. Аналог старого "--mmap --mlock", самый предсказуемый по скорости вариант при достаточном объёме памяти.<br>
- dio - DirectIO: чтение файла модели с диска напрямую, минуя page cache ОС. Работает если доступна поддержка DirectIO на уровне ОС и файловой системы. Аналог старого "--direct-io".<br>

По умолчанию: "--load-mode auto" (автовыбор).

Параметр позволяет вручную указать, в какой памяти (на каком устройстве) хранить конкретные тензоры модели. Правила задаются по шаблонам имен тензоров; если правил несколько, то они перечисляются через запятую. Зачем это нужно. Например в случае с параметром "--n-gpu-layers", в GPU выгружаются целые слои. Выгрузка отдельных тензоров через "--override-tensor" дает более тонкий контроль: можно разнести по устройствам отдельные части слоев. Это может быть целесообразно, например, для MoE-моделей. - вынести тензоры экспертов на менее быстрые устройства (например CPU или менее быстрый GPU), так как они занимают много памяти, а одномоментно работает только часть из них.<br>

**--op-offload, --no-op-offload**<br>
whether to offload host tensor operations to device<br>
(default: true)

Комментарий:<br>
\[Ремарка: описание работы параметра может быть не точным\]

Следует ли переносить операции над тензорами на GPU, если веса лежат в RAM.<br>
Подробнее. Когда веса лежат в RAM (CPU), но вычисления тяжёлые, например матричные умножения при обработке больших батчей (prompt processing), они всё равно выполняются на GPU: веса подгружаются туда на время операции. Как параметр "--cache-type-k", только для подключаемой draft-модели.<br>
Задает тип данных для кэширования значений K (Attention Key). По умолчанию тип данных "f16" (float16). Можно задать квантованные значения, либо тип данных "bf16" (bfloat16), либо более точный "f32" (float32). Тип данных "f32" (float32) потребует под кэш в 2 раза больше памяти, и скорее всего не улучшит заметно качество генерации текста. Меньшие (квантованные) значения потребляют меньше памяти, но хуже по качеству генерации и могут работать медленее из-за дополнительной распаковки значений.

Для некоторых задач квантованные значения K-кэша, например "q8_0", работают не сильно хуже исходных "f16", но в других задачах ухудшение может быть более заметным. Типы квантования "q4_*" сильнее ухудшают качество генерации. Квантование K-кэша обычно ухудшает качество менее заметно, чем V-кэша.

> Справка: Draft-модель - маленькая быстрая модель, которая работает совместно с основной (большой) моделью. Она быстро предсказывает несколько следующих токенов и передаёт их на проверку основной модели. Если предсказание подтверждается, основная модель принимает эти токены, не генерируя их пошагово самостоятельно, что ускоряет общую генерацию текста.

По умолчанию: "--cache-type-k-draft f16" (float16).

env: LLAMA_ARG_CACHE_TYPE_K_DRAFT - переменная окружения в ОС, в ней можно указать значение этого параметра для текущей сессии.
